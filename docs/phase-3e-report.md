Implemented locally on 5 November 2026 (Africa/Johannesburg), on
`feat/self-hosted-migration`, starting with a clean working tree tracking the same
origin branch. No commit, push, merge, deployment, history rewrite, DNS/provider

## 1. Executive summary

The direct review-write gap is closed. Runtime can neither UPDATE submission status
nor INSERT review decisions, including through the former column grants. Reviewers
require live verified Better Auth sessions, approved clergy accounts, current consent,
explicit clergy/reviewer grants and active assignments to the exact current revision.
Admin is no longer an implicit reviewer or confidential-material bypass.

Trusted interactive operator commands issue mailbox-bound one-hour invitations and
manage revision-aware assignments/revocation. The recipient explicitly accepts a
one-time emailed proof before reviewer activation. Assigned reviewers can start,
accept and return work through an atomic, version-checked, idempotent SQL transition.
Authors receive intentionally separate revision-linked feedback; private notes stay
assignment-protected. Accepted non-confidential resources enter the existing repository;
confidential acceptance remains private. All PDF downloads retain mandatory audits.
Four notification types use the existing dynamic sender settings and email providers
through a separate durable domain outbox with encrypted invitation delivery proof.

## 3. Additive migrations and permissions

The active chain now has 26 ledger entries, 22 RLS application tables and four
Better Auth tables. `0020`–`0025` are forward-only additions/refinements. Six generated
snapshots and journal entries accompany them. Historical SQL/snapshots through `0019`
are unchanged. Final audit verifies every applied migration hash against its file.
Guarded migration and grant repetition is safe and preserves existing credentials.

`0021` revokes existing column/table review privileges during migration, before the
post-migration grants are applied. The grant script also explicitly removes them so
repeated setup cannot restore the gap. The ordinary author draft/submit/amend/exclude
functions are unchanged. No broad privileges were added to repair an application error.

New runtime execution is limited to `can_review_submission`, invitation inspection /
acceptance, `decide_review`, `author_review_feedback` and `reviewer_author`. Existing
`is_reviewer`/document-audit entry points retain their signatures with narrower logic.
Runtime may SELECT assignments only through RLS; it has no privileges on invitation,
reviewer event or reviewer notification tables. Operator/trigger/internal functions
have no PUBLIC/runtime execution. Every definer function has fixed `pg_catalog`
search_path and qualified objects. The migration owner remains trusted; no owner
credentials enter web handlers. Better Auth's existing trusted runtime auth-table CRUD
and transaction-local server identity boundary are unchanged.

## 4. Direct privilege-bypass remediation

Previously a live reviewer-context UPDATE(status) could commit separately from a
review INSERT/audit. RLS/column restrictions alone could not enforce atomic evidence.
Both direct capabilities and their write policies are removed. `decide_review` is the
sole runtime review transition and derives its actor internally. It never accepts a
reviewer/role claim, ownership, confidentiality or metadata patch.

Checkpoint A was applied and **5 real restricted-runtime tests passed before any new
reviewer API was implemented**. They prove direct write denial to clergy/reviewer/admin,
no unassigned confidential SELECT/document audit authorization, exact revision scope,
revocation/new-revision denial and preserved owner access. That suite remains passing.
No endpoint was added over a failing Checkpoint A boundary.

## 5. Role and assignment architecture

Global reviewer membership is insufficient. The purpose-specific helper requires live
verified approval/consent/clergy/reviewer state, a non-author current-revision assignment
and an eligible submission state. Submission SELECT, assignment/private-decision SELECT,
document parent visibility and independent download audit authorization enforce it.
Author events remain owner-scoped. Admin retains explicit profile/role/audit reads but
has no confidential submission/document/private-note bypass. Approver/settings-manager
roles remain independent, including on users who legitimately hold multiple capabilities.

Assignments have parent/reviewer FKs, positive revision, explicit state/revocation date,
operator, creation time, correlation ID, inbox index and a partial active uniqueness
constraint. Operator creation locks and verifies the inspected revision; stale prompts
fail. Drafts, self assignments, inactive/unverified reviewers, missing consent, completed
items and duplicate active grants fail. Revocation changes later access without deleting
history. An amendment requires explicit fresh assignment after resubmission. Completed
current-revision access is retained only while an existing assignment remains active.
Future coordination should use a dedicated capability and narrow functions/dashboard,
never unrestricted admin substitution; see the runbook.

## 6. Invitation and mailbox-proof process

An interactive trusted command displays exact registered identity and verification /
approval/clergy state and requires exact confirmation. It never auto-approves a pending
account or grants reviewer authority merely by email. Issuance, immutable operator event,
audit and durable mail intent commit together. No real account is privileged at startup.

Proof uses 32 random bytes, a database SHA-256 digest and one-hour issuance expiry.
The invitation binds exact identity and verified mailbox. Pending invitations are
permanently invalidated by email/verification-state changes. Redemption requires the
server-verified eligible account, possession of proof and explicit acceptance. Row locks
and active-role uniqueness ensure one winner. Consumption, reviewer role, immutable
acceptance history and audit are transactional; injected event failure proves the role
and consumption roll back together. Replays, expiry, revocation and other identities fail.

A separately typed outbox holds AES-256-GCM encrypted proof, identity-bound AAD, random
nonce and an HKDF purpose-separated key from the protected auth secret. The digest table
contains no plaintext token; admin lists/CLI never display proof. Worker success,
cancellation/consumption clear ciphertext. Protected captures necessarily contain the
link; no public inbox exists. Auth-secret loss/rotation requires cancellation/reissue of
pending envelopes, documented in the runbook. No plaintext recovery downgrade exists.

`/reviewer/invitation` uses a fragment-only proof, removes it from the visible URL and
keeps it only in component memory. There are no token GET parameters, SSR serialization,
metadata, analytics or browser credential storage. The page explains responsibilities,
requires explicit acknowledgement and distinguishes same-identity consumed/expired/
revoked links. Sign in first and reopen the original email if navigation lost the proof.
Mutation requests require exact trusted Origin and strict bounded JSON. Unknown/other-
identity links reveal no private account details. New reviewer authority grants no
registration/settings/admin capabilities.

## 7. Reviewer dashboard and actions

`/reviewer` filters/searches only currently authorized assignments with PostgreSQL counts
and 20-row pages. It displays assignment date, title/type/category, confidentiality,
status and revision, including completed current assignments. No global rows/counts are
loaded for client filtering. Empty/loading/error states and refresh checks are provided.

`/reviewer/submissions/{id}` is gated before HTML and through authenticated APIs. It
shows authorized current metadata, necessary author name/title/parish, available included
attachments and current-revision review history. Its PDF links use the original private
Phase 3C endpoint. URL changes cannot authorize unrelated resources. Forms label public
feedback separately from private notes; final actions use accessible Radix confirmation.
Versions/request UUIDs protect conflict/retry behavior. Conflict requires deliberate
refresh. Detail components are keyed by submission to avoid carrying commentary between
items; asynchronous load generations prevent older responses replacing newer loads.

Submitted → under_review starts review. Under_review → accepted requires a private
rationale of at least 20 normalized characters. Under_review → returned requires at
least 20 characters of meaningful intended author feedback. Either field is capped at
10,000 characters. Commentary is saved with immutable actions, not a mutable notepad.
No reviewer edits to authorship, confidentiality, draft metadata or uploads are exposed.

## 8. Author feedback and repository

Author detail responses call a fixed-purpose safe projection selecting outcome, intended
feedback, revision, timestamp and decision ID only. It never selects legacy notes,
reviewer identity or assignment administration. Direct author review-table SELECT is
still denied by RLS. Historical notes remain immutable and private; old rows have NULL
revision instead of fabricated revision claims. Authors see current state, review and
submission timestamps, retained revision feedback, lifecycle evidence and existing
returned-to-draft amendment action. Earlier feedback is never overwritten.

Amendment increments revision and removes old assignment access. Explicit reassignment
is required on the newly submitted revision. Acceptance makes eligible non-confidential
work discoverable through existing authoritative repository predicates without a second
copy/status source. Confidential acceptance never enters shared searches/counts/details.

## 9. Audit, transactions and idempotency

`decide_review` locks live actor auth/profile/roles, parent and assignment, rechecks
eligibility, exact revision, expected version and allowed state. It increments version,
updates status, inserts an immutable decision, appends the author lifecycle snapshot,
adds ID-only security audit and queues any final-decision email in one database
transaction. Four independent injected failures (decision, lifecycle, audit and outbox
insertion) prove all state/evidence roll back together. Resend is never invoked in SQL.

A unique UUID identifies each decision intent. Exact replay validates actor, parent,
assignment, expected version, transition and both commentary fields. Identical concurrent
retries produce one decision/intent; changed-intent reuse fails. Conflicting valid
reviewers have one winner. Revoked/revised-away access cannot use idempotency to bypass
current authorization. Existing append-only triggers protect legacy/new review history;
new reviewer events also block UPDATE/DELETE/TRUNCATE. Operator actor evidence uses
actual database session_user rather than a forged application identity.

Document SELECT and both mandatory pre-byte audit checks share assignment authorization.
Audits contain IDs/actions/outcomes/correlation, never token, private note, file bytes or
storage paths. In-flight transactions may finish before a waiting revocation commits;
already-rendered metadata/transferred bytes cannot be recalled. The trusted-server/GUC
boundary does not protect against stolen runtime credentials, SQL injection or a fully
compromised trusted process. Existing terminal-download-audit limitations remain.

## 10. Notification integration

Separate reviewer outbox kinds are invitation, assignment, accepted and returned. Each
intent is committed with its business action. Common EmailService/Resend/capture,
PostgreSQL sender settings/enable flags and credential fallback are reused. HTML/plain
text messages include trusted BETTER_AUTH_URL links and minimal outcome information,
with no resource contents/titles, private notes or feedback. Assignment delivery checks
live exact-assignment eligibility. Invitation delivery validates current mailbox/proof
state/expiry; expired or invalid proof is cancelled, never sent.

Stable provider keys, five-minute committed SKIP LOCKED leases, persisted first-attempt
sender/reply-to/recipient, backoff capped at an hour and eight attempts make delivery
retryable. Provider I/O follows commit. Failed delivery cannot change review outcomes.
Expired leases recover crashes; cancellation and exhausted attempts remain visible.
No raw provider errors/payloads/links are logged. Tests force safe failures and forbid
external fetch. Actual Resend deliverability is untested. Provider key retention is
finite; ambiguous sends need operator reconciliation and do not imply exactly-once
inbox delivery. Keep trusted origin/configuration stable during pending retries.

## 12. Remaining limitations and release prerequisites

This is a local development implementation, not approval for unrestricted confidential
use. No real reviewer, live Resend request, production change or browser acceptance is
claimed. Pending proof envelopes depend on protected auth-secret backup; rotation needs
cancellation/reissue. The operator/worker uses the guarded local owner outside web
handlers; production requires dedicated least-privilege identities and named operator
auditing. Schedule/monitor both outboxes and reconcile exhausted/ambiguous delivery.
Current-revision assignments do not expose older private notes; those stay operator-
retained. Notes save only with review actions. Fragment loss requires reopening email.

Outstanding requirements remain: approved POPIA wording/retention; durable quarantine/
malware scanning; dedicated production infrastructure/database roles; shared rate
limits; monitoring/alerts; production email scheduling and verified deliverability;
matching DB/private-file backups and restore drills; storage quotas/capacity; and real
browser/mobile/keyboard/screen-reader acceptance. Existing trust, in-flight revocation,
local filesystem and provider idempotency limits are documented in the runbooks.
