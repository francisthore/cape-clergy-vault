# Phase 5A C1 root-cause review · 26 November 2026

**Decision. Keep C1 open and staging blocked.** The bang reader successfully created a marker in the synthetic control directory. This establishes a write-policy gap for that path and the privileged reader. The harness treated the unit settings as proof of its effective mount flags, and its final cleanup could return success after an unexpected write.

## Host evidence

On Ubuntu 24.04 with systemd 255, G1 and G1b passed. N8 passed at 20 seconds and N8b at 40 seconds. Under `!`, all four source and decoy accesses failed, the unit's own credential directory listing succeeded, and `write_ctl` succeeded. The operator rolled back fully. PM2 remained healthy at PID 330461 with zero restarts. The supplied evidence contains neither a C1 `+` outcome nor the failing process's covering mount flags or exact distribution package revision.

## Why the write fits systemd 255

`!` leaves UID/GID setup to the command. The configured mount restrictions and capability bounding set still apply. `PrivateMounts=yes` isolates mount changes from the host. Both namespaces can still refer to the same underlying files. The original reporter performed an ordinary shell redirection in a root-owned 0755 directory. UID 0 has owner write permission there when the covering mount is writable. Root and `CAP_SYS_ADMIN` cannot make that same plain create succeed through a read-only mount. [systemd 255 command prefixes](https://www.freedesktop.org/software/systemd/man/255/systemd.service.html#Command%20lines) · [Filesystem namespacing](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html#File%20System%20Namespacing)

Upstream v255.4 gives a specific explanation. The unit's kernel and proc protections select the API filesystem table, which includes a separate entry for `/run`. When `/run` is already mounted, that entry leaves the existing mount in place. The recursive read-only pass for `/` excludes mount-list subtrees, including this entry. An existing writable `/run` can therefore cover `ctl` even with an empty `ReadWritePaths=`. Explicit masks on sibling paths can operate independently. The recorded host `/run` was writable. This is the leading explanation for the observed write. The missing namespace-local flags prevent attributing the historical result conclusively to this implementation path. [API filesystem selection](https://github.com/systemd/systemd-stable/blob/v255.4/src/core/namespace.c#L1659-L1672) · [Existing /run handling](https://github.com/systemd/systemd-stable/blob/v255.4/src/core/namespace.c#L1188-L1199) · [Recursive exclusions](https://github.com/systemd/systemd-stable/blob/v255.4/src/core/namespace.c#L1819-L1829)

## Production decision and proposed correction

The launcher needs `CAP_SYS_ADMIN` for namespace setup and the fresh proc mount. `NoNewPrivileges=yes` preserves capabilities already held, and `RestrictNamespaces=pid mnt` permits the two namespace types it needs. The root launcher and its resident outer `unshare` supervisor must therefore be trusted. Its child uses `setpriv` to change identity and drop capabilities before Node starts. The entry guard checks PID 1, non-root UID, all five capability sets, `NoNewPrivs` and the proc view. C1 ran only the root reporter. It establishes neither application write access nor sibling credential disclosure. [Launcher](../ops/libexec/cape-vault-ns-launch.example) · [Application entry](../scripts/service-entry.mjs)

The candidate adds one read-only rule for `/run` in each production template and the six corresponding probe units. This covers the runtime tree that the original policy assumed was protected. Web retains its object-store write path. Each worker retains its own writable runtime directory for locks. Scanner storage stays read-only and mail workers' storage stays inaccessible. The launcher needs no code or capability change. Read-only mounts constrain ordinary file operations. Socket connections, propagated submounts and privileged mount administration have their own semantics. [systemd 255 path access rules](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html#ReadOnlyPaths=)

The paired reporters now record namespace identity and covering VFS flags for `/`, `/run` and `ctl`. They use exclusive marker creation, preserve existing entries and return failure on an unexpected access result. The bang case requires a read-only mount and the read-only filesystem error. The plus control must create and remove its marker. Credential contents are discarded.
